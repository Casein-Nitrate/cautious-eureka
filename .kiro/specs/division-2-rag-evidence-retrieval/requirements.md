# Requirements Document: Division 2 - RAG Pipeline & Evidence Retrieval

## Introduction

This document specifies the requirements for Division 2 of the PS 26241 AI-Enabled Career Counselling Platform. Division 2 implements the RAG (Retrieval-Augmented Generation) pipeline with FAISS vector store for evidence retrieval. This division's core responsibility is to ingest MSDE outcome data from CSV files, validate and store evidence, generate embeddings using sentence-transformers, create and manage a FAISS vector store, and provide filtered evidence retrieval. The enhanced Evidence schema supports five critical real-world scenarios by including reality check data (physical demands, typical workday descriptions, trainee quotes), gender context (female enrollment percentages, safety infrastructure), and structured data that enables other divisions to detect echo chamber patterns and guardian veto situations.

## Glossary

- **RAG_Service**: The backend service responsible for CSV ingestion, embedding generation, FAISS index management, and evidence retrieval
- **FAISS_Index**: Facebook AI Similarity Search vector store containing embeddings of all outcome data records
- **Evidence**: Structured outcome data including trade, location, placement rates, earnings, and enhanced fields for edge case handling
- **Embedding**: A dense vector representation of evidence text generated by sentence-transformers (all-MiniLM-L6-v2 model)
- **CSV_Ingestion_Pipeline**: The process of reading MSDE outcome data CSV files and converting rows to Evidence objects
- **Enhanced_Evidence_Schema**: Backward-compatible Evidence schema with additional fields: reality_check, female_enrollment_pct, safety_infrastructure
- **Reality_Check**: Structured data within Evidence containing physical_demand, typical_day, and trainee_quote fields sourced from verified MSDE datasets
- **Evidence_Retrieval_Endpoint**: Internal API endpoint POST /api/internal/evidence/retrieve that accepts filtering criteria and returns ranked Evidence
- **Analytics_Integration**: Division 2 provides evidence data that Division 5 analyzes to detect echo chamber patterns across sessions
- **Guardian_Veto_Data**: Division 2 provides evidence with speaker-tagged concerns that Division 3 analyzes to detect guardian veto situations
- **Embedding_Model**: sentence-transformers model 'all-MiniLM-L6-v2' used for encoding evidence text into 384-dimensional vectors
- **Vector_Search**: Semantic similarity search using cosine distance between query embedding and indexed evidence embeddings
- **Filtering**: Pre-retrieval filtering by trade, district, state, concern category, and concern intent
- **MSDE_Outcome_Data**: Ministry of Skill Development and Entrepreneurship verified outcome dataset containing trade performance data

## Requirements

### Requirement 1: CSV Ingestion from MSDE Outcome Data

**User Story:** As the RAG Service, I want to ingest MSDE outcome data from CSV files, so that I can populate the FAISS vector store with verified evidence.

#### Acceptance Criteria

1. THE RAG_Service SHALL accept CSV files with columns: evidence_id, trade, district, state, placement_rate, earnings_min, earnings_max, currency, data_source, data_period, nsqf_level, progression_path, physical_demand, typical_day, trainee_quote, trainee_quote_source, female_enrollment_pct, safety_infrastructure
2. WHEN a CSV file is provided, THE RAG_Service SHALL validate that all required columns exist (evidence_id, trade, district, state, data_source, data_period)
3. WHEN a CSV row is parsed, THE RAG_Service SHALL convert earnings_min and earnings_max to integers
4. WHEN a CSV row contains progression_path, THE RAG_Service SHALL parse it as a JSON array of strings
5. WHEN a CSV row is missing optional fields, THE RAG_Service SHALL set those fields to NULL
6. WHEN a CSV row has invalid data types, THE RAG_Service SHALL log the error and skip that row
7. WHEN a CSV row contains trainee_quote but trainee_quote_source is missing, THE RAG_Service SHALL log a data quality warning and set trainee_quote to NULL
8. THE RAG_Service SHALL create Evidence objects with enhanced schema fields: reality_check (dict with physical_demand, typical_day, trainee_quote), female_enrollment_pct (string), safety_infrastructure (string)
9. THE RAG_Service SHALL store original Evidence objects in SQLite evidence_repository table for exact retrieval
10. THE RAG_Service SHALL validate that data_source and data_period are present for all evidence records to ensure provenance tracking

### Requirement 2: Embedding Generation Using Sentence-Transformers

**User Story:** As the RAG Service, I want to generate semantic embeddings for each evidence record, so that I can perform similarity-based retrieval.

#### Acceptance Criteria

1. THE RAG_Service SHALL use sentence-transformers model 'all-MiniLM-L6-v2' for embedding generation
2. WHEN generating embeddings, THE RAG_Service SHALL concatenate trade, district, state, placement_rate, earnings range, and nsqf_level into a text representation
3. WHEN enhanced fields exist (physical_demand, typical_day, trainee_quote), THE RAG_Service SHALL include them in the text representation
4. THE RAG_Service SHALL encode the text representation into a 384-dimensional float vector
5. THE RAG_Service SHALL normalize embeddings to unit length for cosine similarity search
6. WHEN the embedding model is not available, THE RAG_Service SHALL return HTTP 503 with error message "embedding model unavailable"
7. THE RAG_Service SHALL batch encode multiple evidence records to improve performance (batch size 32)

### Requirement 3: FAISS Vector Store Creation and Management

**User Story:** As the RAG Service, I want to create and persist a FAISS index, so that I can perform fast semantic search over evidence records.

#### Acceptance Criteria

1. THE RAG_Service SHALL create a FAISS IndexFlatIP (inner product) index for cosine similarity search
2. WHEN adding embeddings to the index, THE RAG_Service SHALL maintain a mapping between FAISS index positions and evidence_id values
3. THE RAG_Service SHALL persist the FAISS index to disk at path: backend/data/faiss_index.bin
4. THE RAG_Service SHALL persist the index-to-evidence_id mapping to disk at path: backend/data/index_mapping.json
5. WHEN the RAG Service starts, THE RAG_Service SHALL load existing FAISS index and mapping if they exist
6. WHEN the FAISS index does not exist, THE RAG_Service SHALL create an empty index
7. THE RAG_Service SHALL provide an administrative endpoint POST /api/internal/evidence/rebuild_index to trigger full index rebuild from CSV
8. WHEN rebuild_index is called, THE RAG_Service SHALL delete existing index, reload CSV data, regenerate embeddings, and recreate FAISS index

### Requirement 4: Evidence Retrieval Endpoint with Filtering

**User Story:** As the Counselling Orchestrator service, I want to retrieve relevant evidence filtered by location and concern, so that I can provide targeted responses to family concerns.

#### Acceptance Criteria

1. THE RAG_Service SHALL expose endpoint POST /api/internal/evidence/retrieve
2. WHEN a retrieval request is received, THE RAG_Service SHALL accept parameters: trade (optional), district (optional), state (optional), concern_category (optional), concern_intent (optional), query_text (optional), top_k (default 5)
3. WHEN filtering parameters are provided, THE RAG_Service SHALL query SQLite evidence_repository to get candidate evidence_ids matching ALL specified filters
4. WHEN no filtering parameters are provided, THE RAG_Service SHALL use all evidence records as candidates
5. WHEN query_text is provided, THE RAG_Service SHALL encode it to an embedding and search FAISS index for top_k most similar vectors among filtered candidates
6. WHEN query_text is not provided, THE RAG_Service SHALL return filtered evidence ordered by placement_rate descending
7. THE RAG_Service SHALL retrieve full Evidence objects from SQLite evidence_repository using the returned evidence_ids
8. THE RAG_Service SHALL return Evidence array with enhanced schema fields included
9. WHEN no evidence matches the filters, THE RAG_Service SHALL return empty evidence array with HTTP 200
10. THE RAG_Service SHALL return HTTP 200 with evidence array upon successful retrieval

### Requirement 5: Enhanced Evidence Schema for Reality Check with Provenance

**User Story:** As the RAG Service, I want to ingest and store reality check information with verified provenance, so that Division 3 can present authentic trainee experiences without fabricated quotes.

#### Acceptance Criteria

1. THE Evidence schema SHALL include optional field reality_check (object)
2. THE reality_check object SHALL contain fields: physical_demand (string), typical_day (string), trainee_quote (string), trainee_quote_source (string)
3. WHEN reality_check data exists for a trade, THE RAG_Service SHALL include it in retrieved Evidence objects only if trainee_quote_source is present
4. WHEN reality_check data does not exist or lacks source provenance, THE RAG_Service SHALL set reality_check to NULL
5. THE physical_demand field SHALL describe physical requirements from verified sources (e.g., "8-hour standing shifts, lifting 25kg equipment")
6. THE typical_day field SHALL describe a realistic workday from verified sources (e.g., "6 AM start, outdoor installation work, client site visits")
7. THE trainee_quote field SHALL contain a first-person quote from a current trainee or recent graduate
8. THE trainee_quote_source field SHALL identify the source dataset and collection period (e.g., "MSDE Trainee Experience Dataset 2025")
9. THE data_source and data_period fields SHALL track provenance for all evidence components, not just trainee quotes

### Requirement 6: Enhanced Evidence Schema for Gender Context

**User Story:** As the RAG Service, I want to ingest and provide evidence with female enrollment and safety infrastructure data, so that Division 3 can address gender-family concerns with relevant evidence.

#### Acceptance Criteria

1. THE Evidence schema SHALL include optional field female_enrollment_pct (string)
2. THE Evidence schema SHALL include optional field safety_infrastructure (string)
3. WHEN female enrollment data exists, THE RAG_Service SHALL format it as percentage string (e.g., "35%")
4. WHEN safety infrastructure data exists, THE RAG_Service SHALL include detailed description (e.g., "24/7 CCTV monitoring, female warden on-site, separate accommodation")
5. WHEN gender-related data does not exist, THE RAG_Service SHALL set female_enrollment_pct and safety_infrastructure to NULL
6. WHEN concern_category is "gender_family", THE RAG_Service SHALL prioritize returning evidence records that contain non-NULL female_enrollment_pct and safety_infrastructure fields, with ranking still determined by semantic relevance and location match
7. THE RAG_Service SHALL NOT apply arbitrary thresholds (e.g., "only return if female_enrollment_pct > 20%") but instead return all relevant evidence and allow Division 3 to interpret the data

### Requirement 7: Backward-Compatible Evidence Schema

**User Story:** As the RAG Service, I want to maintain backward compatibility with Division 3, so that existing evidence retrieval continues working while enhanced fields are optional.

#### Acceptance Criteria

1. THE Evidence schema SHALL include all original fields from API contract v1.2: evidence_id, trade, district, state, placement_rate, earnings_min, earnings_max, currency, data_source, data_period, nsqf_level, progression_path
2. THE Evidence schema SHALL mark enhanced fields as optional: reality_check, female_enrollment_pct, safety_infrastructure
3. WHEN Division 3 requests evidence, THE RAG_Service SHALL return enhanced Evidence objects
4. WHEN Division 3 processes Evidence, THE enhanced fields SHALL be safely ignored if not needed
5. THE RAG_Service SHALL validate Evidence objects against Pydantic schema before returning
6. WHEN Evidence validation fails, THE RAG_Service SHALL log the error and exclude that evidence from results

### Requirement 8: Async Operations and Database Integration

**User Story:** As the RAG Service, I want to perform database operations asynchronously, so that I can handle concurrent evidence retrieval requests efficiently.

#### Acceptance Criteria

1. THE RAG_Service SHALL use async/await pattern for all database operations
2. THE RAG_Service SHALL use async SQLAlchemy with aiosqlite driver
3. THE RAG_Service SHALL create evidence_repository table with columns: evidence_id (VARCHAR 50 PRIMARY KEY), trade (VARCHAR 100), district (VARCHAR 100), state (VARCHAR 100), placement_rate (VARCHAR 20), earnings_min (INTEGER), earnings_max (INTEGER), currency (VARCHAR 10), data_source (VARCHAR 200), data_period (VARCHAR 50), nsqf_level (VARCHAR 50), progression_path (JSON), physical_demand (TEXT), typical_day (TEXT), trainee_quote (TEXT), trainee_quote_source (TEXT), female_enrollment_pct (VARCHAR 10), safety_infrastructure (TEXT), embedding_text (TEXT), created_at (TIMESTAMP)
4. THE RAG_Service SHALL create indexes: idx_evidence_trade, idx_evidence_district, idx_evidence_state on evidence_repository table
5. THE RAG_Service SHALL support at least 50 concurrent retrieval requests without performance degradation

### Requirement 9: Error Handling and Logging

**User Story:** As a backend developer, I want comprehensive error handling and logging, so that I can diagnose issues with embedding generation, FAISS search, and data quality.

#### Acceptance Criteria

1. WHEN CSV ingestion encounters a malformed row, THE RAG_Service SHALL log the row number and error details and continue processing
2. WHEN embedding generation fails, THE RAG_Service SHALL log the evidence_id and error message
3. WHEN FAISS index file is corrupted, THE RAG_Service SHALL log the error and create a new empty index
4. WHEN evidence_repository query fails, THE RAG_Service SHALL return HTTP 500 with error message "database error"
5. WHEN FAISS search returns fewer than top_k results, THE RAG_Service SHALL return all available results without error
6. THE RAG_Service SHALL log all API requests to evidence/retrieve endpoint with parameters and result count
7. THE RAG_Service SHALL log performance metrics: embedding generation time, FAISS search time, database query time

### Requirement 10: Data Validation and Quality Checks

**User Story:** As the RAG Service, I want to validate ingested data quality, so that only verified, complete evidence is available for retrieval.

#### Acceptance Criteria

1. WHEN ingesting CSV data, THE RAG_Service SHALL validate that placement_rate is in format "XX%" or NULL
2. WHEN ingesting CSV data, THE RAG_Service SHALL validate that earnings_min <= earnings_max
3. WHEN ingesting CSV data, THE RAG_Service SHALL validate that evidence_id is unique
4. WHEN validation fails, THE RAG_Service SHALL log the validation error with evidence_id and field name
5. THE RAG_Service SHALL provide endpoint GET /api/internal/evidence/stats that returns: total_evidence_count, trades_covered, districts_covered, evidence_with_reality_check_count, evidence_with_gender_data_count
6. THE RAG_Service SHALL return HTTP 200 with statistics upon successful query

### Requirement 11: FAISS Index Optimization

**User Story:** As the RAG Service, I want to optimize FAISS index performance, so that evidence retrieval completes in under 100ms for typical queries.

#### Acceptance Criteria

1. THE RAG_Service SHALL use FAISS IndexFlatIP for exact search (datasets under 100,000 records)
2. WHEN the evidence repository exceeds 100,000 records, THE RAG_Service SHALL migrate to IndexIVFFlat with 100 clusters
3. THE RAG_Service SHALL measure and log search latency for each retrieval request
4. WHEN average search latency exceeds 200ms over 100 requests, THE RAG_Service SHALL log a performance warning
5. THE RAG_Service SHALL load FAISS index into memory at startup
6. THE RAG_Service SHALL not reload FAISS index on every request

## Special Requirements Guidance: Property-Based Testing

**Where Property-Based Testing Applies in Division 2**:

1. **Text Representation for Embedding** (Requirement 2):
   - Property: Concatenating evidence fields should always produce valid text (no NULL injection, consistent format)
   - Test: Generate random Evidence objects, verify text representation is non-empty and contains expected fields

2. **Filtering Logic** (Requirement 4):
   - Property: Filtering by trade/district/state should return only matching records
   - Metamorphic property: Filtering by trade + district should return subset of filtering by trade only
   - Test: Generate random evidence sets, apply filters, verify result set properties

3. **Enhanced Field Handling** (Requirements 5, 6, 10):
   - Property: Enhanced fields being NULL should not break evidence retrieval or schema validation
   - Test: Generate Evidence objects with random NULL/non-NULL combinations of enhanced fields, verify all pass validation

4. **Vector Search Ranking** (Requirement 4):
   - Property: Most similar evidence should be ranked higher (if A is more similar than B, A should appear before B)
   - Test: Generate query embeddings, verify ranking order matches similarity scores

**Where Integration Tests Apply**:

1. **CSV Ingestion** (Requirement 1): Use 2-3 example CSV files (valid, missing columns, malformed data, missing provenance)
2. **FAISS Index Persistence** (Requirement 3): Create index, save, reload, verify integrity
3. **Database Operations** (Requirement 8): Standard CRUD operations on evidence_repository
4. **API Endpoint Responses** (Requirements 4, 10): Call endpoints with example payloads, verify response schemas
5. **Provenance Validation** (Requirement 5): Verify trainee_quote is NULL when trainee_quote_source is missing

## Division Responsibilities and Boundaries

**Division 2 Core Responsibility:**
Division 2 is the **Evidence Repository and Retrieval Service**. Its responsibility is to:
1. Ingest and validate MSDE outcome data from CSV
2. Store verified evidence in SQLite evidence_repository
3. Generate embeddings and maintain FAISS index
4. Provide filtered, ranked evidence retrieval via API
5. Ensure data quality and provenance tracking

**What Division 2 Provides (Data Layer):**
- Enhanced Evidence objects with reality_check, female_enrollment_pct, safety_infrastructure
- Filtered evidence retrieval by trade, location, concern category/intent
- Semantic search via FAISS vector similarity
- Data provenance (data_source, data_period, trainee_quote_source)
- Evidence repository statistics

**What Division 2 Does NOT Do (Intelligence Layer):**
- **Session Summary Generation** → Division 1/Division 4 responsibility
- **Echo Chamber Detection Logic** → Division 5 (analytics) + Division 3 (counselling decision)
- **Guardian Veto Detection** → Division 3 (counselling orchestrator)
- **Concern Classification** → Division 3 (counselling orchestrator)
- **Evidence Interpretation** → Division 3 (counselling orchestrator)

**Division Integration Pattern:**
```
MSDE CSV Data
      ↓
Division 2: Ingest → Validate → Store → Embed → Index
      ↓
Division 2: Retrieve (filtered + ranked)
      ↓
Division 3: Classify concerns → Retrieve evidence → Generate response → Detect patterns (echo chamber, guardian veto)
      ↓
Division 5: Analyze cross-session patterns → Feed insights to Division 3
      ↓
Division 1: Store session/concern/evidence history
      ↓
Division 4: Translate and format for user experience
```

**Key Principle:**
Division 2 provides **data**; other divisions provide **intelligence**. This separation ensures Division 2 remains focused on evidence quality, retrieval performance, and schema extensions, while reasoning about echo chambers, guardian vetoes, and session summarization belongs to divisions with access to cross-session context and counselling logic.
